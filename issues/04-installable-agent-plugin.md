# 04 — Installable agent plugin served by the site

**What to build:** An agent in any Claude Code session can install a plugin
from learn.joshhale.me and use one skill to turn the work it just did into a
lesson Josh can open on his phone. This is the `quiz` plugin re-pointed at the
portal: the skill authors `lesson.json`, attacks its own draft, validates it
with the downloaded validator, creates a private draft through the API with
Josh's bearer token, and prints the learning URL.

The site serves the plugin as static files and as one downloadable archive,
generated at build time from the resolver, the authoring rules and the
diagnostics reference so the plugin can never disagree with the server. The
capability document links to it. A human page explains the three install
routes: Claude Code plugin install from the site's marketplace manifest, a
`git clone` of the served directory, and copying the single skill directory.

The skill keeps the plugin `SKILL.md` steps: establish the source, read the
authoring rules, write the lesson, attack the draft as a separate pass, run the
validator until clean, then submit. Replace the build-and-render steps with:
resolve against the API, create the draft, report the URL. Provenance is
required; the skill fills client, harness, model, client version and a session
reference, using `unknown` where the harness exposes nothing.

The token comes from the `LEARN_TOKEN` environment variable. The skill never
prints it and never writes it into the lesson or a log. The plugin is served
from the site only; do not add it to any other marketplace in this stage.

**Demo path:** In a fresh Claude Code session in another repository, install
the plugin from the site, ask for a lesson on the diff just written, and get
back a URL that opens the new lesson's overview once ticket 08 lands. Until
then, the API returns the created revision.

### Decisions

- Plugin root is `public/plugin` itself, so `claude plugin validate public/plugin`
  validates the plugin manifest. The marketplace manifest sits at
  `public/plugin/marketplace.json`, not in `.claude-plugin/`, because the
  validator validates a marketplace instead of the plugin when both are there.
- Marketplace source is `archive` with `sha256`, because relative-path sources
  fail in URL marketplaces and the Claude Code source types do not include a
  plain git URL served by us other than `url`; the archive is deterministic so
  the pin is stable. The archive and the repository hold the plugin tree without
  the marketplace file, which would otherwise pin itself.
- Deterministic bytes: stored ZIP entries with one fixed DOS date; Git loose
  objects as stored deflate blocks with a fixed author and date. No compressor
  runs, so a runtime upgrade cannot move the committed files.
- The plugin's texts name the canonical origin `https://learn.joshhale.me`
  (static files cannot know the request origin); the page at `/plugin` and the
  capability document use the request origin.
- `deno.json` test task gains `--allow-run=git,claude,which`,
  `--allow-net=127.0.0.1` and `--allow-env=LEARN_TOKEN,LEARN_BASE_URL` for the
  clone and script tests. The `claude` test skips when the CLI is absent.
- `/plugin` is documented in OpenAPI as a discovery route rather than added to
  the browser-only set, so the route-coverage test keeps its shape.
- `.env.example` on `main` contains an unresolved merge marker from ticket 07;
  not touched here.
